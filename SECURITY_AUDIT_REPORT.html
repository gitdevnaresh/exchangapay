What the assessment found

This is a fintech application that holds customer crypto balances, issues payment cards, displays full card numbers and PINs, and processes identity documents for KYC. That risk profile demands a high security bar. The application does not currently meet it.

The single biggest problem is not any individual bug — it is a systemic absence of secrets management. A live third-party API secret, a Sentry organisation token, a real login token, Auth0 client identifiers, Firebase configuration, and the key used to sign the app itself are all committed to the repository in plain text. Anyone with repository access — or anyone who downloads the app and unzips it — obtains them.

What is genuinely done well. This audit is not a verdict on the team's competence. Several things here are better than the scores suggest:

  • The migration from JavaScript crypto-js to native react-native-quick-crypto is careful, documented, byte-compatible with the backend, and verified.
  • The decryption memoisation cache correctly reasons about determinism, key-scoping, and why encryption must not be cached.
  • Auth tokens are stored in the Keychain/Keystore rather than plain storage.
  • allowBackup="false", ad-ID removal, and ATS arbitrary-loads-disabled are all correct.
  • Authentication uses Auth0 Authorization Code + PKCE — the right choice for a native app.
  • The build tooling notes (CMake/NDK pinning, Jetifier rationale, lockfile tracking) explain why, not just what.

Fix These First — The Three That Matter Most

If you do nothing else this week, do these three. Each is a small change with an outsized effect.

Critical#1

Replace the app signing key

android/app/build.gradle:117 · android/app/debug.keystore (committed to git)

In plain English: Your app is signed with the practice key that ships free with Android Studio. Its password is literally the word android, and every Android developer in the world already has an identical copy. On top of that, the key file itself is committed to your git repository.

Why that's serious: Android decides whether an app update is legitimate by checking that it was signed with the same key. Anyone can build a fake ExchangaPay — one that steals passwords or rewrites withdrawal addresses — sign it with this key, and phones will install it as an official update, inheriting your app's stored login tokens.

What to do

  1. Generate a real key, offline, and store it in a password manager or secrets vault — never in git.
  2. Point the release build at it via environment variables.
  3. Enrol in Google Play App Signing so Google holds the master key and yours becomes rotatable.
  4. Treat every APK you have already distributed as compromised; plan a forced update once a properly signed build exists.
keytool -genkeypair -v -keystore exchangapay-release.jks \
  -keyalg RSA -keysize 4096 -validity 10000 -alias exchangapay
Critical#2

Fix the environment selector — every build points at the test server

Environment.js:69

In plain English: The function that picks which server the app talks to accepts an argument ("prod", "tst") and then throws it away, always returning the test configuration. Every build of this app — including any you believe is production — talks to tstapi.exchangapay.com and the test Auth0 login tenant.

Why that's serious: If a build has reached real customers, they have completed real KYC — uploading genuine passports and ID documents — into a test system. Test environments typically have wider team access, weaker retention rules, and less log hygiene than production.

⚠ Time-sensitive

Check today whether real customer identity documents are sitting in the test environment. If they are, this may be a notifiable data breach with a 72-hour reporting clock. Involve your Data Protection Officer before doing anything else.

What to do

// Environment.js — before
export const getAllEnvData = (envName) => {
  return ENV["tst"] || ENV.prod;        // ← envName ignored
};

// after
const ENV_NAME = process.env.APP_ENV || "prod";   // injected at build time
export const getAllEnvData = (envName) => ENV[envName || ENV_NAME] || ENV.prod;

Then add real build-time environment selection: react-native-config with git-ignored .env files, Android product flavours, and iOS build configurations — each with its own Firebase file and Auth0 tenant.

Critical#3

Stop sending login tokens to crash reporting

src/utils/ApiService.ts:87

In plain English: Every time an API call fails, the app sends the user's live login token — plus the complete request and response — to Firebase Crashlytics and Sentry. A login token is the digital equivalent of a house key: whoever holds it is that user until it expires.

Why that's serious: Anyone with access to your Firebase or Sentry console can read live customer session tokens out of crash reports and use them to access those accounts. And because a Sentry access token is committed to your repository (finding C-02), that "anyone" includes people who only have repo access — no device needed.

What to do

  1. Delete the token line immediately — one line, no downside.
  2. Replace whole-body logging with an allow-list of safe diagnostic fields.
  3. Purge existing Crashlytics and Sentry data, and treat every token logged so far as compromised.
// src/utils/ApiService.ts — remove these
token:    token ?? "unknown",                    // ← DELETE
response: JSON.stringify(response?.data),        // ← DELETE
request:  JSON.stringify(config?.data ?? {}),    // ← DELETE

// replace with a shared scrubber used by BOTH Crashlytics and Sentry
const SAFE_KEYS = new Set(["traceId", "errorCode", "correlationId"]);
const redact = (o) => (o && typeof o === "object")
  ? Object.fromEntries(Object.entries(o)
      .map(([k, v]) => [k, SAFE_KEYS.has(k) ? v : "[REDACTED]"]))
  : "[REDACTED]";

Critical Findings

Eight findings that individually justify blocking a release. Each includes a plain-English explanation, the realistic attack, a production-ready fix, and how to verify it.

CriticalC-01

Live support-chat API secret hardcoded in the shipped app

src/screens/Chatbot/chatscreen.tsx:44-48 · src/services/chatService.js:184 (duplicated)

In plain English

The password that proves your app is allowed to talk to Kommo — your support-chat provider — is written directly into the app's JavaScript, in two separate places. Anyone who downloads the app and unzips it can read it in about thirty seconds. No hacking skill required; unzip and grep are enough.

This is a server-class credential: it identifies your whole application to Kommo, not one user. It should never have left your backend.

// src/screens/Chatbot/chatscreen.tsx
const config = {
    secretKey: '60d0c569…redacted…3ab4a',   // ← HMAC signing key
    channelId: '30778ba5-1242-…',
    accountId: 'e393e15b-d500-…'
};

What an attacker does

  1. Downloads the APK and extracts the secret with strings.
  2. Reads any customer's support conversation — the history endpoint is keyed on the customer ID, which is guessable or enumerable.
  3. Impersonates any customer — the chat-creation call accepts an arbitrary name, email and phone supplied by the caller.
  4. Harvests what fintech support conversations contain: transaction IDs, wallet addresses, partial card data, identity documents, and account-recovery discussion — then uses it for account takeover.

How to fix it · effort: medium

  1. Rotate the Kommo secret today. Assume it has been public for the lifetime of every build containing it.
  2. Move all signing to your backend. Add two endpoints that authenticate with the existing bearer token, derive the conversation ID from the server-side session (never from a client-supplied value), sign the request, and proxy to Kommo: 
    POST /api/v1/Support/Chat/Message
GET  /api/v1/Support/Chat/History
  3. Delete src/services/chatService.js from the app and replace the KommoChatAPI usage in chatscreen.tsx with calls to the new endpoints.
  4. Purge from git history — rotation is not enough if the repo is ever made public or a former contributor kept a copy: 
    git filter-repo --path src/services/chatService.js --invert-paths
# then force-push and have everyone re-clone

The principle to adopt: a mobile app is a public, untrusted binary. Any credential that grants privileges beyond the currently logged-in user must live only on a server. The Sumsub token flow in this codebase already does this correctly — copy that pattern.

Verify the fix

  • grep -rn "60d0c569" . returns nothing, including in git history.
  • The old Kommo secret is revoked and confirmed rejected by Kommo.
  • Support chat still works, with all traffic going through your own backend.
  • Requesting another user's conversation history returns 403 from your backend.
CriticalC-02

Sentry organisation access token committed to the repository

ios/sentry.properties:2 (tracked in git)

In plain English

An access token for your Sentry account is sitting in a file that is committed to git. Sentry is where your crash reports go. This token is used during iOS builds to upload source maps — and it typically carries broad permissions across the whole organisation.

Why this one is especially bad: combined with finding C-07 (login tokens written into crash reports), this token lets someone read live customer session tokens without ever touching a phone.

auth.token=sntrys_eyJpYXQiOjE3NjEzNzQ3NDku…redacted…
defaults.org=exchangapay

What an attacker does

  1. Gains repository read access — a compromised developer account, an over-permissive fork, an accidental public push, or simply being a former contributor who copied it before access was revoked.
  2. Uses the token against the Sentry API to read every crash and error event — which, per C-07, contain full API requests, responses, and bearer tokens.
  3. Downloads your uploaded source maps, fully de-minifying the app and handing over readable source.
  4. Optionally tampers with releases, corrupting the data you rely on to detect incidents.

Revoking someone's repository access does not revoke a token they already copied.

How to fix it · effort: small

  1. Revoke the token now in Sentry → Settings → Auth Tokens. Issue a replacement scoped to project:releases only, as an organisation token rather than a personal one.
  2. Remove the file from git and ignore it. The org and project names are not secret — only the token is, and sentry-cli reads it from an environment variable natively: 
    git rm --cached ios/sentry.properties
echo "ios/sentry.properties" >> .gitignore

# ios/sentry.properties keeps only the non-secret parts:
defaults.org=exchangapay
defaults.project=exchangapay
defaults.url=https://sentry.io/

# the token comes from CI:  SENTRY_AUTH_TOKEN=${{ secrets.SENTRY_AUTH_TOKEN }}
  3. Purge from git history with git filter-repo or BFG.
  4. Audit Sentry's access log for this token since 2025-10-25 (its issue date) to see whether it has already been used from somewhere unexpected.

Verify the fix

  • The old token returns 401 when used against the Sentry API.
  • git log --all -p -- ios/sentry.properties shows no token value.
  • An iOS release build still uploads source maps successfully, using the CI-provided variable.
  • Sentry's audit log shows no unexpected use of the old token.
CriticalC-03

Release builds are signed with the committed debug keystore

android/app/build.gradle:104-122 · android/app/debug.keystore (tracked in git)

In plain English

Android decides whether an app update is genuine by checking it was signed with the same key as the installed version. Your release builds are signed with the debug key — the practice key that ships with the Android SDK, whose password is literally the word android. Every Android developer on earth has an identical copy, and yours is committed to the repository as well.

The React Native template's own warning comment about this is still sitting in the file, unheeded. The release pipeline that was recently deleted even printed a warning about it in every release's changelog — and shipped anyway.

signingConfigs {
    debug {
        storeFile file('debug.keystore')
        storePassword 'android'          // ← the universal SDK default
        keyAlias 'androiddebugkey'
        keyPassword 'android'
    }
}
buildTypes {
    release {
        // Caution! In production, you need to generate your own keystore file.
        signingConfig signingConfigs.debug      // ← release signed with the DEBUG key
        minifyEnabled enableProguardInReleaseBuilds   // ← which is false (C-08)
    }
}

What an attacker does

  1. Takes any released APK, or pulls debug.keystore from the repo — or just uses their own copy of the SDK's default debug keystore.
  2. Builds a trojanised ExchangaPay: a keylogger over the PIN screen, exfiltration of the stored login token, or silent rewriting of the destination wallet address before a withdrawal is submitted.
  3. Signs it with the same key. Android's update-integrity check passes. The malicious build installs over the legitimate app, inheriting its data directory, its stored tokens, and the user's trust.
  4. Distributes it by SMS ("update required"), sideload site, or third-party store — behaviour the app's own force-update screen already conditions users to comply with.

Second consequence: if this app is ever published to Google Play with this key, the signing identity can never be cleanly changed for that listing.

How to fix it · effort: medium

  1. Generate a real key, offline, with a strong passphrase: 
    keytool -genkeypair -v -keystore exchangapay-release.jks \
  -keyalg RSA -keysize 4096 -validity 10000 -alias exchangapay
  2. Store it in a secrets manager (Vault, AWS Secrets Manager, or GitHub encrypted secrets as base64) and materialise it only inside the CI runner.
  3. Split the signing configuration: 
    signingConfigs {
    debug { /* unchanged — debug builds only */ }
    release {
        storeFile     file(System.getenv("EXCHANGA_KEYSTORE_PATH") ?: "dummy.jks")
        storePassword System.getenv("EXCHANGA_KEYSTORE_PASSWORD")
        keyAlias      System.getenv("EXCHANGA_KEY_ALIAS")
        keyPassword   System.getenv("EXCHANGA_KEY_PASSWORD")
    }
}
buildTypes {
    release {
        signingConfig signingConfigs.release
        minifyEnabled true              // see C-08
        shrinkResources true
        proguardFiles getDefaultProguardFile("proguard-android-optimize.txt"),
                      "proguard-rules.pro"
    }
}
  4. Enrol in Google Play App Signing so Google holds the master key and your upload key becomes rotatable.
  5. Remove the keystore from git and purge it from history: 
    git rm --cached android/app/debug.keystore
  6. Force all users onto a properly signed build using the existing neoMobileVersioncheck force-update mechanism once one exists.

Verify the fix

  • apksigner verify --print-certs app-release.apk shows your certificate, not androiddebugkey.
  • No keystore file exists anywhere in the working tree or git history.
  • A release build fails cleanly if the signing environment variables are absent.
  • Play App Signing is enabled on the listing.
CriticalC-04

Hardcoded login token and an authentication-bypass fallback

src/screens/SplashScreen.tsx:175-250

In plain English

The splash screen contains a "temporary login" function holding a real login token for an actual customer account on your Auth0 tenant. It skips the entire login flow.

The fallback is worse than the token. When the call using that token fails, the code does not stop — it invents a fully-verified, KYC-approved user and navigates straight into the Dashboard. It fabricates exactly the flags every onboarding gate checks: email verified, phone verified, KYC complete, state Approved.

// on failure, instead of stopping…
dispatch(isLogin(true));
dispatch(setUserInfo({
    role: "Customer",
    isEmailVerified: true,
    isPhoneNumberVerified: true,
    isKYC: true,                      // ← fabricated
    customerState: "Approved",        // ← fabricated
    customerKycRequiredorNot: false,
}));
navigation?.dispatch(CommonActions.reset({ routes: [{ name: "Dashboard" }] }));

What an attacker does

  • If the button is reachable at all — even hidden behind a long-press or a conditional — anyone who finds it in the bundle gets an authenticated session with no credentials.
  • If not, they attach Frida (no root detection, no obfuscation, debug-signed build) and call the function directly, or patch the bundle to invoke it on launch.
  • The bigger lesson: this code proves that setting one Redux value is all that stands between a user and the Dashboard. Whether that also lets them transact depends entirely on whether your backend re-checks KYC on every financial endpoint — the app provides no protection either way.

How to fix it · effort: small (code) / medium (server-side)

  1. Delete onTempLoginPress entirely — the token, the function, and the whole catch fallback. There is no safe version of this.
  2. Revoke that account's sessions and refresh tokens in Auth0.
  3. Make every failure path fail closed. Never fabricate user state: 
    } catch (e) {
  await clearPersistedState();
  setError("Sign-in failed. Please try again.");
}
  4. Enforce KYC and AML server-side. Every financial endpoint — top-up, crypto withdrawal, card issuance, statement export — must independently verify the caller's KYC status and account state from the backend's own record, derived from the token's subject. The client's navigation gating is user experience, not security.
  5. Add a CI gate so this cannot come back: 
    grep -rEn 'eyJ[A-Za-z0-9_-]{10,}\.eyJ[A-Za-z0-9_-]{10,}' src/ && exit 1

Verify the fix

  • No JWT-shaped string exists anywhere in src/; the CI gate passes.
  • The old token is rejected by the API.
  • Calling a financial endpoint with a token whose account is not KYC-approved returns 403 from the server.
  • Every authentication failure path lands on the login screen, never on the Dashboard.
CriticalC-05

Every build points at the test environment

Environment.js:68-74

In plain English

The function that selects which backend the app talks to takes an argument — and ignores it, always returning the test configuration. Callers passing "prod" still get "tst".

So every build of this app, including any you consider production, sends its API traffic to tstapi.exchangapay.com and logs users in against the test Auth0 tenant. Three other pieces of configuration confirm it independently: the Android package is com.exchangapay.tst, the Auth0 domain placeholder is the tst tenant, and both Firebase files point at exchangapay-tst-f570a.

export const getAllEnvData = (envName) => {
  return ENV["tst"] || ENV.prod;      // envName accepted, then discarded
};                                     // ENV["tst"] is always truthy, so the
                                       // "|| ENV.prod" fallback is dead code

Why this is serious

  • Real KYC documents in a test system. Customers upload genuine passports and IDs. Test environments typically have wider team access, weaker retention rules, and less log hygiene — a serious data-protection failure.
  • Mainnet addresses against a test backend. A separate hardcoded ENV = "tst" in the helpers selects mainnet crypto address patterns, so the app accepts real BTC/ETH/TRON/SOL addresses while pointed at a non-production system.
  • Production is invisible. Sentry is tagged environment: "development" and is disabled on the prod config anyway, so genuine production errors are not reported at all.

This is not an attack — it is the current behaviour of every build.

How to fix it · effort: large

  1. Make the function honour its parameter, with a safe default: 
    const ENV_NAME = process.env.APP_ENV || "prod";   // injected at build time
export const getAllEnvData = (envName) => ENV[envName || ENV_NAME] || ENV.prod;
  2. Add real build-time environment selection. There is currently no mechanism at all:

Password encryption uses 10 rounds instead of 600,000

In plain English

Key derivation deliberately runs a slow calculation many times so that guessing becomes expensive. The industry minimum for this algorithm is 600,000 rounds. Your code uses 10 — roughly 60,000× too few. On a modern graphics card, 10 rounds is effectively instant.

The rest of the implementation is correct: random salt, random IV, proper output format. The migration to native crypto was done carefully — the iteration count was simply carried over from legacy code and never re-justified.

  const nonce  = QuickCrypto.randomBytes(NONCE_SIZE);
  const cipher = QuickCrypto.createCipheriv("aes-256-gcm", keyBuf, nonce);
  const ct     = Buffer.concat([cipher.update(plainText, "utf8"), cipher.final()]);

Fix: React.lazy + Suspense for everything except splash, dashboard and the error screens; split into feature-scoped nested navigators. Gain: large — cold start and memory.
2Bundle bloat Three chart libraries, two date libraries (~70 KB vs ~2 KB), eleven redundant packages, and x86 architectures shipped in release builds.
Fix: consolidate per L-02; ship an Android App Bundle; set reactNativeArchitectures=armeabi-v7a,arm64-v8a; enable shrinkResources. Gain: large — download size.
3No list virtualisation tuning Across 12 lists: keyExtractor is present everywhere (good), but getItemLayout, initialNumToRender, maxToRenderPerBatch and windowSize are used zero times. Transaction history and chat are the ones that hurt.
Fix: add the tuning props for uniform-height rows; wrap renderItem in useCallback and rows in React.memo; consider FlashList for variable heights. Gain: medium — scroll smoothness.
4Redundant work every render Only 5 useMemo calls across 53,000 lines. Concretely: a useEffect calls a function inside its dependency array (causing repeat API calls on the withdrawal screen); the chat screen builds a new API client object on every render; the legacy reducer deep-clones state with JSON.parse(JSON.stringify()) on every dispatch.
Fix: memoise the derived value, the API client and the user object; remove the deep clones. Gain: medium.
5Network inefficiency Chat polls every 60 s even when idle and backgrounded, despite push already delivering the same signal. The IP lookup runs on the offline branch. No response caching or request deduplication.
Fix: push-triggered refresh; fix the branch; add React Query or RTK Query. Gain: medium — battery, data, server load.
6Startup sequence The notification permission is requested on first launch with no explanation, which drives high denial rates. Three separate mount effects compete with the first render.
Fix: request notification permission contextually after first successful login, with a rationale; consolidate the mount effects.

Data protection (GDPR)

Two items may already require action from your Data Protection Officer:

  • Real KYC data in a test environment (C-05) — identity documents processed in a non-production system.
  • The committed Sentry token (C-02) — combined with C-07, it grants access to customer session tokens and personal data. If it has been used from an unexpected location, that is a personal-data breach.

Also outstanding: no consent mechanism for analytics and crash collection (Art. 6); the ipinfo.io data recipient is undeclared (Art. 13/14); processor agreements should be confirmed for Sentry, Google, Kommo, Sumsub and ipinfo.io (Art. 28); and session replay of financial screens would require a Data Protection Impact Assessment (Art. 35).
